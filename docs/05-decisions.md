# 설계 결정 기록

## D-001. 프로젝트 성격

상태: 확정

이번 프로젝트는 운영 서비스가 아니라 인턴 발표용 기술 검증 PoC다.

## D-002. 테스트 도서

상태: 확정

- 앨리스 동화책과 유사한 합성 도서 1권을 사용한다.
- 팀원이 AI를 활용해 본문과 삽화를 제작한다.
- 사람이 내용과 텍스트 및 이미지 일관성을 검수한다.
- 분석 시스템은 제작 과정에 참여하지 않고 완성된 파일만 입력받는다.

## D-003. OCR 및 이미지 추출

상태: 확정

- 회사에 이미 존재하는 기능으로 가정한다.
- 이번 프로젝트에서는 구현하지 않는다.
- 로컬 파일 입력을 회사 기능의 출력 대체물로 사용한다.

## D-004. 대화 시점

상태: 확정

- 작품의 마지막 사건이 끝난 직후로 고정한다.
- 장별 대화 시점 선택은 구현하지 않는다.
- 원문의 pageNumber, paragraphIndex, sourceOrder는 보존한다.

## D-005. 등장인물 추출과 대화 허용

상태: 확정

- AI가 책에 등장하는 고유 인물 후보를 추출한다.
- AI는 narrativeRole을 추천할 수 있다.
- 사람이 최종 역할과 chatEnabled를 결정한다.
- 이번 PoC에서는 한 명만 대화 가능하게 설정한다.
- 특정 인물 이름을 코드에 하드코딩하지 않는다.

## D-006. 주요 인물 자동 선정

상태: 제외

다음 지표를 이용한 대화 적합도 자동 계산은 향후 기능으로 둔다.

- 본문 등장량
- 대사량
- 주요 사건 참여 수
- KG 관계 수
- 성격과 동기의 근거량
- 종료 시점 지식의 충분함
- 이미지 등장 횟수와 외모 정보량

PoC에서는 사람이 직접 선택한다.

## D-007. 텍스트 원본과 RAG

상태: 확정

- 원문 문단은 일반 데이터 저장소에 보존한다.
- RAG는 문단을 의미 검색하기 위한 색인으로 사용한다.
- 같은 페이지 텍스트가 필요하면 RAG가 아니라 pageNumber로 직접 조회한다.
- 캐릭터 프로필은 DB에서 직접 조회한다.

## D-008. 초기 RAG 기준선

상태: 확정

초기 검색 방식은 다음과 같다.

```text
문단별 임베딩
→ 유사 문단 상위 K개 검색
→ 각 문단의 앞뒤 N개 문단 확장
→ 겹치는 범위 병합
```

K와 N은 설정값으로 분리한다.

청킹과 검색 방식은 이후 교체 가능하도록 인터페이스로 분리한다.

## D-009. 이미지 분석 문맥

상태: 확정

이미지 분석 시 다음을 함께 전달한다.

- 이미지
- 같은 페이지의 텍스트
- 텍스트에서 추출된 개체 후보 목록

이미지만으로 인물 이름을 확정하지 않는다.

## D-010. 멀티모달 정보 출처

상태: 확정

각 정보에는 출처 유형을 기록한다.

```text
TEXT
IMAGE
TEXT_AND_IMAGE
INFERRED
```

알 수 없는 정보는 UNKNOWN으로 남긴다.

## D-011. 이미지 정보의 해석 범위

상태: 확정

- 한 장면의 표정을 지속적인 성격으로 확정하지 않는다.
- 한 장면의 옷차림을 지속적인 외모로 확정하지 않는다.
- 실내에서 보이지 않는 실외 날씨를 추측하지 않는다.
- 반복 관찰된 외모는 지속적 특징 후보로 올릴 수 있다.

## D-012. 사건과 관계

상태: 확정

- 개체 후보를 먼저 추출한다.
- 그 이후 사건과 관계를 추출한다.
- 이번 PoC에서는 결말 시점의 주요 관계를 사용한다.
- 시점별 관계 변화 저장은 향후 기능으로 둔다.

## D-013. 최종 캐릭터 프로필

상태: 확정

- 사건과 관계 분석 이후 생성한다.
- 텍스트, 이미지, 사건, KG를 함께 활용한다.
- 명시된 정보와 추론된 정보를 구분한다.
- 결말 직후 시점의 인물로 생성한다.

## D-014. KG 구현 기술

상태: 확정

- Neo4j와 같은 별도 그래프 DB를 사용하지 않는다.
- PostgreSQL의 KnowledgeEntity 및 KnowledgeRelation 테이블로 구현한다.
- 캐릭터 중심의 직접 관계 조회를 우선한다.
- 책 1권과 대화 캐릭터 1명 규모에서 별도 DB의 ID 연결, 동기화, 트랜잭션 및 운영 복잡도를 추가하지 않는다.
- 향후 다단계 관계 탐색이 핵심 기능이 되면 그래프 DB를 다시 검토할 수 있다.

## D-015. RAG 저장 기술

상태: 확정

- 기본 데이터베이스로 PostgreSQL을 사용한다.
- 일반 관계형 데이터와 RAG 임베딩을 한 데이터베이스에서 관리한다.
- 임베딩 저장과 벡터 유사도 검색에는 pgvector를 사용한다.
- PostgreSQL과 pgvector는 로컬 Docker Compose로 실행하며, Windows에 PostgreSQL을 직접 설치하지 않는다.
- MySQL 또는 MariaDB로 변경하거나 두 종류의 관계형 DB를 함께 운영하지 않는다.

## D-016. 외부 AI 제공자

상태: 부분 확정

- 텍스트 생성과 멀티모달 이미지 분석은 OpenAI를 사용한다.
- 초기 기본 모델은 비용 효율을 우선해 `gpt-5.6-luna`를 사용한다.
- 모델 ID는 환경변수로 분리해 품질 비교 시 다른 모델로 교체할 수 있게 한다.
- 임베딩 모델은 D-027에서 `text-embedding-3-small`로 확정했다.

API 키는 `OPENAI_API_KEY` 환경변수에서만 읽고 저장소에 보관하지 않는다.

## D-018. 백엔드 기반 기술

상태: 확정

- Java 17과 Spring Boot 3.5.x를 사용한다. 정확한 patch 버전은 프로젝트 생성 시점에 결정한다.
- Gradle 단일 백엔드 프로젝트로 구성한다.
- Spring Web MVC, MyBatis, JDBC, PostgreSQL JDBC Driver, Flyway, Spring Actuator를 사용한다.
- OpenAPI 문서화는 Springfox가 아니라 Spring Boot 3.x와 호환되는 springdoc-openapi 계열을 사용한다.
- 테스트에는 JUnit 5와 Spring Boot Test를 사용한다.
- 회사 기존 Spring Boot 2.5.2 및 Gradle 멀티 프로젝트 구성을 그대로 적용하지 않는다.

## D-019. 초기 백엔드 제외 기술

상태: 확정

- 회원가입과 로그인이 없으므로 Spring Security, JWT, 회원 인증 및 권한 관리를 제외한다.
- 캐시, 분산 세션 및 요청 제한 관리가 필요하지 않으므로 Redis를 제외한다.
- Actuator는 기본 상태 확인에 사용하지만 Prometheus 연동은 제외한다.
- 실제 비동기 처리나 캐싱 문제가 확인되면 Redis 도입을 다시 검토한다.

## D-020. 프론트엔드 기반 기술

상태: 확정

- Next.js 15, React 19, TypeScript를 사용한다.
- 서버 상태 관리는 TanStack Query, UI 구성은 Tailwind CSS, Radix UI, lucide-react를 사용한다.
- 초기 단일 화면은 React 상태와 TanStack Query로 시작하며 Zustand는 전역 상태가 복잡해질 때 검토한다.
- 초기 PoC는 한국어 화면을 기준으로 하며 다국어 리소스 구조는 제외한다.
- OCR 및 업로드 전처리용 PDF.js, Tesseract.js, heic2any와 범위 밖의 Three.js, HLS.js, MindAR는 제외한다.

## D-021. 외부 AI API 연동 방식

상태: 확정

OpenAI 공식 Java SDK와 Responses API를 사용한다. 현재 SDK 버전은 4.43.0이다. 애플리케이션 내부에는 제공자 독립 인터페이스를 두어 분석 도메인 코드가 SDK 타입에 직접 의존하지 않게 한다. 구조화 출력은 SDK가 생성하는 JSON Schema를 사용하고, 로컬 이미지는 data URL로 변환해 전달한다.

## D-022. 텍스트 개체 후보 추출 단위와 재실행

상태: 확정

- 원문 문단을 설정 가능한 배치로 나눠 분석하며 초기 배치 크기는 20개다.
- 앞 배치의 후보 이름과 별칭을 다음 요청에 전달하고, 서버에서도 정규 이름과 별칭 중복을 비교해 같은 개체를 병합한다.
- AI가 반환한 유형, 신뢰도, `sourceOrder`, 실제 지칭 표현을 서버에서 검증한다.
- 모든 배치의 분석과 검증이 성공한 뒤 한 트랜잭션으로 해당 책의 기존 PENDING 후보를 새 결과로 교체한다.
- 관계, 사건 및 대화 가능 여부는 이 단계에서 판단하지 않는다.
- 검수 상태를 수정하는 기능이 추가되기 전에 승인 또는 병합된 후보의 재실행 정책을 다시 결정한다.

## D-023. 페이지 이미지 분석과 초기 병합

상태: 확정

- 멀티모달 분석은 페이지당 한 번 실행하며 같은 페이지의 원문, 현재 개체 후보와 모든 이미지를 함께 전달한다.
- 기존 후보와 명확히 일치할 때만 이미지 mention을 같은 후보에 연결하고, 불확실한 개체는 `originSource=IMAGE` 후보로 별도 저장한다.
- 관찰 사실은 `ExtractedFact`에 원본 이미지, 출처, 신뢰도 및 상태와 함께 저장한다.
- 상태는 `CONFIRMED`, `CANDIDATE`, `UNKNOWN`, `CONFLICT`만 허용한다.
- 재실행은 이미지 기반 mention, 후보와 관찰 사실만 교체하며 텍스트 후보와 근거는 유지한다.
- 모든 페이지의 호출과 검증이 성공한 뒤 DB 교체 트랜잭션을 실행한다.
- 관계와 사건은 이미지 분석 단계에서 만들지 않는다.

## D-024. 검수 전 KG 구축과 근거

상태: 확정

- Task 6은 짧은 PoC 도서의 전체 원문, 개체 후보와 이미지 관찰 사실을 한 번의 구조화 요청으로 분석한다.
- 검수 전 `EntityCandidate`는 승인하지 않고 PENDING 상태의 `KnowledgeEntity`로 투영한다.
- 사건은 `StoryEvent`와 EVENT 유형 `KnowledgeEntity`로 함께 표현하고 참여자는 `EventParticipant`로 연결한다.
- 개체 사이의 1단계 직접 관계만 `KnowledgeRelation`으로 저장한다.
- 원문 근거 `sourceOrder`와 이미지 근거 `pageNumber+imageOrder`는 서버에서 실제 원본 ID로 검증·변환한다.
- 모든 분석과 검증이 성공한 뒤 사건과 KG만 한 트랜잭션으로 교체한다.
- 긴 책의 부분별 사건 통합 전략은 현재 PoC에서 확정하지 않는다.

## D-025. 등장인물 검수와 활성 캐릭터

상태: 확정

- AI의 narrativeRole 추천은 참고값이며 후보 상태를 자동 승인하거나 거절하지 않는다.
- 사람 요청만 후보를 APPROVED, REJECTED, MERGED로 변경하고 최종 역할과 chatEnabled를 결정한다.
- 승인된 후보만 Character로 생성하며 mention에서 CharacterAlias를 구성한다.
- 병합 시 source 후보의 mention, 관찰 사실 및 KG 연결을 target 후보로 이동하고 source 후보는 MERGED 이력으로 남긴다.
- 책마다 chatEnabled Character는 한 명만 허용하며 DB 부분 유일 인덱스와 서비스 검증을 함께 사용한다.
- 활성 캐릭터가 정확히 한 명이면 책 상태는 `CHARACTERS_REVIEWED`, 없으면 `KG_BUILT`로 유지 또는 복귀한다.
- 초기 검수는 REST API로 수행하고 화면은 후속 Next.js 작업에서 구현한다.

## D-026. 최종 캐릭터 프로필과 근거

상태: 확정

- 책에서 유일한 chatEnabled Character만 프로필 생성 대상으로 한다.
- 프로필 시점은 결말 직후인 `AFTER_FINAL_EVENT`로 고정한다.
- 초기 고정 프로필 필드는 JSON이 아니라 `character_profile`의 개별 TEXT 컬럼으로 저장한다.
- 프로필 값과 근거는 분리하고 `profile_evidence`에 profileField, 원문·이미지 ID, sourceType, EXPLICIT/INFERRED 및 신뢰도를 저장한다.
- 근거 없는 특성은 생성하지 않고 확인할 수 없음으로 표현한다.
- 모든 AI 응답과 근거 검증이 성공한 뒤 해당 Character의 기존 프로필을 한 트랜잭션으로 교체한다.
- 생성된 systemPrompt는 초안으로 저장하며 실제 대화 조립은 Task 10에서 다시 검토한다.

## D-027. 초기 RAG 임베딩과 검색 전략

상태: 확정

- 비용과 PoC 규모를 고려해 OpenAI `text-embedding-3-small`을 사용하고 기본 출력인 1536차원을 저장한다.
- 초기 검색값은 `topK=3`, `contextWindow=2`이며 환경변수로 조정한다.
- 원문 문단 하나를 `PARAGRAPH` RagDocument 하나로 색인하고, 모델과 전략 버전을 함께 저장한다.
- pgvector 코사인 거리로 상위 문단을 정확 검색한 뒤 sourceOrder 기준 앞뒤 문단을 확장하고 겹치거나 이어진 범위를 병합한다.
- 책 한 권 규모에서는 벡터 인덱스를 만들지 않는다. 데이터 규모나 지연 문제가 확인되면 HNSW 등을 검토한다.
- 색인은 모든 임베딩의 개수와 차원을 검증한 뒤 기존 색인을 한 트랜잭션으로 교체한다.
- 검색 전략은 인터페이스로 분리해 이후 검색 방식이나 인덱스 변경이 서비스 API에 영향을 주지 않게 한다.

## D-028. 초기 캐릭터 대화와 근거 검증

상태: 확정

- 초기 대화 API는 대화 이력을 저장하지 않는 단발성 질문·답변으로 구현한다.
- 활성 캐릭터의 최종 프로필은 DB에서 직접 조회하고, 질문별 RAG 검색 결과와 캐릭터에 연결된 1단계 KG 관계만 프롬프트에 포함한다.
- 캐릭터의 1인칭과 `AFTER_FINAL_EVENT` 시점을 유지하고, 제공한 원문과 KG로 뒷받침되지 않는 사실·감정·동기를 만들지 않도록 지시한다.
- AI는 답변, 근거 충분 여부, 사용한 문단 ID와 관계 ID를 구조화해 반환한다.
- 서버는 인용 ID가 실제 제공한 RAG·KG 문맥에 속하는지 검증하고, 근거가 있다고 한 답변에는 하나 이상의 유효한 근거를 요구한다.
- 근거 부족 응답은 AI가 만든 문구를 사용하지 않고 서버의 고정된 모름 응답으로 교체한다.
- 발표용 응답에는 사용 근거 ID, 검색된 원문 범위와 직접 KG 관계를 디버그 정보로 포함한다.
- 첫 정상 응답 후 책 상태를 `CHAT_READY`로 변경한다.

## D-030. Gradio 파이프라인 QA 워크벤치

- 사람 검수 단계는 자동으로 건너뛰지 않으며 후보별 역할, 승인·거절과 대화 가능 여부를 직접 선택한다.

- 단계 재실행 시 기존 분석 데이터가 교체될 수 있으며, OpenAI 호출 단계에는 비용 발생 가능성을 화면에 표시한다.

- Next.js의 기존 `/qa` 화면과 QA 전용 API 타입은 제거하고, 발표 화면에서 별도 Gradio 주소를 새 창으로 연다.

## D-031. 채팅방 단기 대화 문맥과 질문 재작성

상태: 확정

- 대화 기록은 DB에 저장하지 않고 현재 브라우저 화면의 React 상태에만 둔다. 새로고침, 책 변경, `새 대화` 선택 시 초기화한다.
- 최근 3턴(최대 6개 메시지)만 API로 보내며, 질문은 1000자, 과거 메시지 하나는 2000자, 전체 기록은 10000자로 제한한다. 범위를 넘으면 오래된 대화부터 제외한다.
- 첫 질문은 기존처럼 원래 질문으로 바로 RAG 검색한다. 대화 기록이 있으면 매번 LLM으로 독립 질문을 만들고 그 질문으로 RAG를 검색한다.
- 독립 질문을 만들 수 없을 만큼 대상이 모호하면 RAG를 생략하고 캐릭터 말투로 대상을 되묻는다. 후보가 있으면 구체적으로, 없으면 일반적으로 묻는다.
- 질문 재작성 호출 또는 응답 검증이 실패하면 원래 질문으로 기존 단일 질문 경로를 수행하고 debug에 fallback 여부를 남긴다.
- 최종 응답에는 원래 질문과 독립 질문을 함께 제공하되, 답변 대상은 원래 질문으로 유지한다.
- 대화 기록과 이전 캐릭터 답변은 대명사와 생략 표현을 해석하는 문맥으로만 사용하며 사실 근거로 인정하지 않는다. 새 사실은 계속 RAG 문단 또는 KG 관계 ID로 검증한다.
- 응답 유형은 근거 기반 답변 `ANSWER`, 대상 확인 질문 `CLARIFICATION`, 관련 근거 없음 `UNKNOWN`으로 구분한다.

## D-032. 질문 의도 판정과 일상 대화

상태: 확정

- 기존 독립 질문 재작성 LLM을 별도 호출 추가 없이 질문 해석 LLM으로 확장해 모든 입력에서 `FACTUAL` 또는 `SOCIAL` 의도를 함께 판정한다.
- 책의 사건, 장소, 인물, 관계, 성격, 감정, 경험을 묻는 입력은 `FACTUAL`이며 기존 RAG·KG 근거 검증을 유지한다.
- 인사, 감사, 사과, 작별, 칭찬, 짧은 반응처럼 책의 사실 확인이 필요 없는 입력만 `SOCIAL`로 처리한다.
- `SOCIAL`은 RAG와 KG 조회를 생략하고 캐릭터 프로필과 최근 대화 문맥만으로 답하되, 새로운 책 속 사실을 만들지 못하도록 제한한다.
- `SOCIAL` 응답은 `grounded=false`이고 근거 ID를 허용하지 않으며, API `responseType`에 `SOCIAL`을 추가한다.
- 질문 해석 호출이나 구조 검증이 실패하면 기존 B안대로 `FACTUAL`로 간주하고 원래 질문으로 RAG 검색을 수행한다.

## D-033. 검증된 프로필 추론을 사용한 캐릭터 답변

상태: 확정

- 캐릭터의 성격, 가치관, 목표, 관계, 선호와 가상 상황 질문에는 최종 프로필과 `profile_evidence`를 답변 근거로 함께 제공한다.
- `EXPLICIT`은 직접 확인된 사실로, `INFERRED`는 원문·이미지 행동에서 도출한 제한적 해석으로 구분한다.
- `INFERRED` 근거로 선호·의향을 답할 때는 명시적 사실처럼 단정하지 않고 캐릭터 말투 안에서 추론의 불확실성을 자연스럽게 표현한다.
- 최종 AI 응답은 사용한 `profileEvidenceId`를 반환하고, 서버는 현재 캐릭터 프로필에 실제 존재하는 ID인지 검증한다.
- 원문 문단과 KG 관계가 직접 검색되지 않아도 관련 프로필 근거가 있으면 근거 기반 `ANSWER`가 될 수 있다.
- 관련 프로필·행동 근거가 전혀 없는 새로운 취향, 계획, 감정은 계속 생성하지 않으며 `UNKNOWN`으로 처리한다.
